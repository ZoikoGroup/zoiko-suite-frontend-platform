# governance-decision-log-svc — the theory

The append-only evidence store behind every governed decision in the suite.

| | |
|---|---|
| **Service** | `governance-decision-log-svc` |
| **Local port** | `8083` |
| **Console page** | `/admin/governance` |
| **Frontend client** | `lib/api/governance.ts` |
| **Writes** | One (`POST /v1/decisions`) — append-only, no update, no delete |

### Routes

| Method | Route | Surfaced in the console |
|---|---|---|
| `GET` | `/v1/decisions` | Yes — *Decision log* |
| `GET` | `/v1/decisions/{decision_id}` | Yes — *Look up a decision* |
| `POST` | `/v1/decisions` | Yes — *Record a decision* |
| `POST` | `/v1/decisions/{id}/replay` | No |
| `GET` | `/v1/decisions/{id}/replay-manifests` | No |

## 1. The governance layer — the theory

### The problem it exists to solve

In a normal system, business logic and permission logic are tangled together. Payroll code asks "is this allowed?", gets a yes, and pays. The answer is used and thrown away. Six months later someone asks "why was £48,000 released to that account?" — and nobody can answer, because the only trace is the payment itself.

The governance layer splits one action into three separate concerns:

| Concern | Who owns it | Question it answers |
|---|---|---|
| **Doing** | The domain service (payroll, AP, procurement) | Did the money move? |
| **Deciding** | `policy-svc`, `authorization-svc`, `workflow-svc` | Is this allowed? |
| **Remembering** | **`governance-decision-log-svc`** | What was decided, and on what basis? |

This service is only the third one. It **makes no decisions** — it is a witness, not a judge. That distinction runs through its whole design.

### The core doctrine: an outcome without its basis is not evidence

This is the single most important idea in the service. Storing `DENIED` is nearly worthless — it tells you what happened but not why, so it can neither be defended to an auditor nor debugged by an engineer. Every record must therefore carry three things:

```
outcome    ← WHAT was decided        (GRANTED / DENIED / ESCALATED)
rule_basis ← WHY it was decided      (the rule that produced the outcome)
context    ← WHAT IT WAS BASED ON    (the facts at decision time)
```

`rule_basis` is `NOT NULL` in the schema and non-optional in the handler for exactly this reason. The console enforces it too, which is why the record form refuses an empty rule basis with *"an outcome without its basis is not evidence."*

The third one matters more than it looks. A rule reference alone is not reproducible — "spend limit exceeded" means nothing unless you also know the limit *was* £25,000 and the request *was* £48,000. `evaluation_context` captures that frozen snapshot of the inputs.

### Append-only: the property that makes it evidence

Evidence you can edit is not evidence. This is enforced at three levels:

1. **No routes.** There is no `PUT`, `PATCH` or `DELETE` on a decision. The API surface makes mutation unexpressible.
2. **A database trigger.** Migration `000003` installs a `BEFORE UPDATE OR DELETE` trigger that raises an exception. The migration comment explains why this and not `REVOKE`: every service connects as a Postgres superuser, and **a superuser bypasses privilege checks but not triggers**. The trigger is the actual enforcement.
3. **Doctrine for corrections.** A wrong decision is corrected by *recording a new decision* that references the original — never by changing the old row. The old, wrong record stays visible forever. That is the point: the log shows what was actually believed at the time, including mistakes.

### Two different times, deliberately kept apart

```
decided_at  ← when the decision was MADE, upstream (caller supplies)
stored_at   ← when this service WROTE IT DOWN (database default NOW())
```

These diverge constantly — a decision made during a nightly batch and logged 40 minutes later, or a historical decision backfilled from a legacy system. Collapsing them would destroy the audit trail's chronology. `stored_at` is stored but never returned by the API; it exists so late-arriving evidence can be detected.

If a caller omits `decided_at`, the service defaults it to its own receipt time — which quietly conflates the two. That is why the console always stamps it explicitly rather than letting the default fire.

### Idempotency as an evidence property

`decision_id` is **supplied by the caller**, not generated by the service, and it is the primary key. This makes recording safe to retry: a network timeout followed by a retry produces one row, not two.

The status code says which happened:

- **`201`** — new evidence was appended
- **`200`** — this `decision_id` was already recorded; nothing was written

That distinction is not cosmetic. A log that reports a replay as a fresh success lets one decision masquerade as two, which inflates the record. Hence the console's separate `recorded` and `replayed` states, with different wording and colour.

There is a subtlety the code calls out. Because `decision_id` is client-supplied and the primary key is the id *alone*, a naive implementation would answer "already recorded" for an id another tenant had used — making the endpoint both an existence oracle (leaking that another tenant used that id) and a black hole (silently dropping the write). The store therefore checks whether the row is *yours* and raises a conflict instead.

### Tenant isolation

Every decision is tenant-owned. The tenant comes from the **verified `X-Tenant-Id` header**, never from the request body — a body naming another tenant is refused rather than honoured. Enforcement is layered:

- Postgres RLS via `set_config('app.tenant_id', …)` per transaction, forced in migration `000006`
- an explicit `tenant_id = $2` in the lookup query, as defence-in-depth

Observed behaviour: a read carrying another tenant's id returns `[]`, a lookup by id returns `404`, and a request with no tenant header at all is refused with `400 missing_tenant_id`.

### Linkage: how one decision joins the wider story

Four id fields exist purely to stitch a decision into its surroundings:

| Field | Required | Purpose |
|---|---|---|
| `decision_id` | Yes | This record's own identity, and its idempotency key |
| `correlation_id` | Yes | Groups everything one originating request did, across all services |
| `causation_id` | No | The specific event or earlier decision that *caused* this one |
| `workflow_instance_id` | No | Which running workflow this happened inside |

`workflow_instance_id` and `causation_id` were originally buried inside the `evaluation_context` JSON blob; migration `000004` promoted them to real indexed columns. The reasoning is worth noting — "find every decision made during workflow instance X" is a real query, and answering it via a JSONB scan does not scale.

## 2. The three console features

### A. Decision log — browse and filter the evidence

`GET /v1/decisions` → newest first, always a JSON array (never `null`).

**What it is for:** the investigative surface. *"Show me everything that was refused for this entity last week."* It is the feature most people will use daily.

**Inputs** — all optional, all **AND-composed**, all **exact equality** (no partial or fuzzy matching):

| Input | Filters on | Notes |
|---|---|---|
| `actor` | `actor_id` | Who triggered the action |
| `entity` | `legal_entity_id` | Which legal entity — *not* the tenant |
| `action` | `action_type` | e.g. `PAYROLL_RELEASE` |
| `rule_basis` | `rule_basis` | The full stored string, exactly |
| `from` | `decided_at` ≥ | **RFC3339 only** — `2026-09-07T00:00:00Z`. Anything else → `400 invalid_from` |
| `to` | `decided_at` ≤ | Same → `400 invalid_to` |
| `limit` | page size | Default **50**, silently capped at **200** |
| `offset` | page start | Zero-based |

> **Trap 1 — every filter is exact.** Because each is equality AND-ed with the rest, four plausible-looking values can match nothing. `rule_basis=SPEND-LIMIT` returns zero rows when the stored value is `SPEND-LIMIT-V3:pv-8f2c1a` — it is not a prefix search. The console names every active filter when a search returns empty, so the over-narrow one is visible.

> **Trap 2 — `limit` is capped silently.** Ask for 500, get 200, with nothing saying it was truncated. The console clamps its own requests to 199 so it can ask for `limit + 1` and detect a next page without hitting the ceiling.

**What comes back:** the full record for each decision, including the `evaluation_context` blob.

### B. Look up a decision — fetch one record by its id

`GET /v1/decisions/{decision_id}`

**What it is for:** you are holding an id from somewhere else — an error message, a support ticket, another service's response, a row in the log — and you need that exact record. It exists because a route per decision would be absurd, and because `decision_id` is the reference people quote to each other.

**Input:** exactly one — the `decision_id` string.

**Responses:**

- **`200`** — the record
- **`404`** — not visible to your tenant

That `404` is genuinely ambiguous and the console says so: it means *either* no such decision exists *or* it belongs to another tenant. The lookup is tenant-scoped, so from the caller's position those two are indistinguishable.

### C. Record a decision — append one immutable row

`POST /v1/decisions` — the only write in the entire service.

**What it is for:** normally *services* call this automatically — `policy-svc` appends a decision on every evaluation. Recording by hand is for backfilling a decision made outside the suite (a board approval, a legacy import). Once written it is **indistinguishable from one a service wrote**, which is a deliberate design choice and a reason to be careful with it.

#### The inputs split three ways

**① What you type in the console**

| Field | Required | Type / limit | Meaning |
|---|---|---|---|
| Action type | **Yes** | `VARCHAR(128)` | What was being decided — `PAYROLL_RELEASE` |
| Outcome | **Yes** | `VARCHAR(32)` | The verdict. **No CHECK constraint** — see below |
| Rule basis | **Yes** | `VARCHAR(256)` | The rule that produced it — `SPEND-LIMIT-V3:pv-8f2c1a` |
| Actor | No | `VARCHAR(64)` | Who triggered it. Blank → your principal |
| Legal entity | No | `VARCHAR(64)` | Blank → your session entity |
| Anything else worth recording | No | `JSONB` | The facts it was based on |

**② What the console generates for you** — and why it does not let you type them:

| Field | Why it is generated |
|---|---|
| `decision_id` | A fresh UUID. A human-chosen value would eventually collide across unrelated decisions, and at that point the second one is silently swallowed as a replay and never recorded at all |
| `decided_at` | Stamped now, rather than letting the service default it and conflate deciding with logging |
| `correlation_id` | A fresh UUID per submission |
| `tenant_id` | Taken from your verified session, never typed |

**③ What the envelope requires as headers** (the console sends all of these):

| Header | Rule |
|---|---|
| `X-Principal-Id` | Required, or `401 missing_principal` — checked before anything else |
| `X-Tenant-Id` | Required, or `400 missing_tenant_id` |
| `X-Request-Id` | Required |
| `X-Source-Channel` | Required, **and from a fixed set**: `api`, `import`, `integration`, `mobile`, `scheduled_job`, `system`, `web` |
| `Idempotency-Key` | Required for material state changes (INV-08) |
| `X-Purpose-Context` | Required for governed sensitive access — here, `GOVERNANCE_DECISION_RECORD` |

Miss any and the response is `400 envelope_incomplete` with a `violations` array naming each field and why — returned before the handler runs at all.

#### The outcome column is free text

`outcome VARCHAR(32) NOT NULL`, with **no CHECK constraint**. The service accepts *any* string. The documented set is `GRANTED` / `DENIED` / `ESCALATED`, and the console offers only those three — but that is the console narrowing its own form, **not** the service refusing.

This is why the readable rendering has an "unrecognised outcome" path. A value like `PROVISIONALLY_OK` from a legacy import lands in the review bucket, keeps its raw text visible, and is explicitly labelled as *not* an approval. Silently mapping an unknown outcome to "Allowed" would be the worst possible failure in an evidence log.

#### Everything that can refuse the write

```
401  missing_principal        no X-Principal-Id
400  envelope_incomplete      missing/invalid envelope header
400  missing_field: <name>    a required body field was empty
400  invalid_json             evaluation_context wasn't parseable
403  authorization_denied     authorization-svc said no
403  tenant scope mismatch    body named a tenant that isn't yours
503  authz_unavailable        authorizer unreachable — fails CLOSED
503  store_unavailable        database unreachable; nothing written
200  (not an error)           this decision_id was already recorded
201  success                  new evidence appended
```

Two of these deserve emphasis:

- **Writes are authorized.** `CreateDecision` calls `authorization-svc` for the action `GOVERNANCE_DECISION_RECORD` and refuses on denial.
- **It fails closed.** If the authorizer cannot be reached, the write is refused with `503` rather than allowed through. For an evidence log, refusing to record is safer than recording something unauthorized.

## 3. What exists in the service but has no UI

Two routes the console does not surface:

- **`POST /v1/decisions/{id}/replay`** — re-evaluates a past decision against the **exact policy version it originally used**, and records whether the replay reproduced the original outcome.
- **`GET /v1/decisions/{id}/replay-manifests`** — the append-only history of those replays.

This is reproducibility auditing: proving a decision was not just recorded but is *re-derivable* from the rules as they stood at the time. Currently limited to `APPROVAL_THRESHOLD` action types — anything else returns *"replay not implemented for this decision's action_type"* rather than faking a replay that did not happen.

## 4. How the theory shapes the console

The readable rendering follows directly from the doctrine above:

| UI element | Backing field | Why it is placed there |
|---|---|---|
| Headline sentence | `outcome` + `action_type` | The verdict is the first thing anyone needs |
| Meaning paragraph | derived from `outcome` | The outcome vocabulary is not self-explanatory to a non-developer |
| "Why it was decided that way" | `rule_basis` | Given top billing — an outcome without its basis is not evidence |
| "Details recorded with the decision" | `evaluation_context` | The frozen snapshot of the inputs, rendered as a plain list |
| Stored code beside every plain phrase | `outcome`, `action_type` | The evidence must never be *replaced* by this console's reading of it |

That last row is the rule the whole rendering obeys: labels are presentation, values are evidence. Keys are humanised and values are formatted, but nothing stored is altered or dropped, and the raw JSON stays one disclosure away at every call site.
